# openSUSE (OBS project and zypper repository)

openSUSE Leap and Tumbleweed consume RPM packages through zypper. This
directory holds the recipe for an openSUSE Build Service (OBS) package and the
zypper repository OBS publishes from it.

OBS is the build system and the repository host at once: the project builds
`bitty.spec` against the Leap and Tumbleweed repositories, then publishes
repository metadata (`repodata/`) that `zypper addrepo` consumes. There is no
separate signing or upload pipeline in this repository.

## Support level

The zypper channel is **best-effort, not supported** in the sense of
`packaging/README.md` `Support evidence`: no release `verify-install` leg
covers openSUSE, so a package that builds and installs is not support
evidence. `packaging/opensuse.md` labels it the same way for users. Promoting
it means adding an openSUSE leg to the release `verify-install` matrix first.

## Layout

| File | Purpose |
| --- | --- |
| `bitty.spec` | RPM recipe: source build of `crates/bitty-terminal`, desktop entry, AppStream metainfo, hicolor icons, compiled terminfo. |
| `_service` | OBS source service: checks out the release tag, produces `bitty-<version>.tar.gz`, keeps `Version` aligned. Every service is `mode="disabled"`. |
| `README.md` | This file: project layout, submission, repository publication. |

The recipe pins the `0.0.30` line like the sibling recipes (`packaging/alpine/APKBUILD`,
`packaging/gentoo/`, `packaging/void/`). `Version`, the `_service` revision,
and the `%changelog` entry move together at release time.

OBS adds two generated files to the package directory that never live here:
the source tarball and its `.sha256` sidecar. Source checksums are regenerated
at tag time, not hand-edited: `osc service disabledrun` rewrites the tarball,
`osc addremove` picks up the new `.sha256`, and the commit carries both.

## What needs an OBS account or token

No credential is stored in this repository, and nothing here reads one.

| Step | Needs an OBS account? | Needs a token? |
| --- | --- | --- |
| Reading this recipe, XML/RPM lint checks | No | No |
| `osc service disabledrun`, `osc build --local-package` | No | No |
| `osc checkout` of a project that already exists | Yes | No (oscrc credentials or an interactive login) |
| Creating `home:<user>:bitty` and its repositories | Yes | No (same oscrc credentials) |
| `osc commit`, `osc submitrequest` | Yes | No (same oscrc credentials) |
| Publishing the zypper repository | No (OBS publishes automatically) | No |

OBS authenticates with the username/password or token in `~/.config/osc/oscrc`
or with `osc -A <apiurl>`. Keep both outside the tree; CI never needs them
because the OBS package is built and published by OBS itself.

## Local checks without an account

```sh
# XML well-formedness of the source service.
python3 -c 'import sys, xml.etree.ElementTree as ET; ET.parse(sys.argv[1])' packaging/opensuse/_service
xmllint --noout packaging/opensuse/_service

# Spec parse (only where the RPM tooling exists; the CI gate skips it).
rpmspec -q --srpm packaging/opensuse/bitty.spec

# The repository gate that runs in `just check`.
bash scripts/tests/check-distro-recipes.test.sh
```

`osc build --local-package` compiles the package in a local chroot without an
OBS account. It still needs `osc`, network access to the distribution
repositories, and the OBS build tooling (`build`, `podman` or `systemd-nspawn`):

```sh
cd /path/to/osc-package-dir   # holds bitty.spec, _service, the tarball
osc service disabledrun        # regenerate bitty-<version>.tar.gz + .sha256
osc build --local-package openSUSE_Tumbleweed x86_64
```

## Project layout in OBS

One OBS project holds both distributions:

```text
home:<user>:bitty           # the OBS project (metadata set with `osc meta prj`)
`-- bitty/                  # the package directory, what `osc checkout` gives you
    |-- bitty.spec          # from this directory
    |-- _service            # from this directory
    |-- bitty-<version>.tar.gz         # generated by the source service
    `-- bitty-<version>.tar.gz.sha256  # generated by OBS
```

The project meta enables the repositories the package is built and published
for:

```xml
<project name="home:<user>:bitty">
  <title>Bitty terminal</title>
  <description>Bitty packages for openSUSE Leap and Tumbleweed.</description>
  <person userid="<user>" role="maintainer"/>
  <repository name="openSUSE_Tumbleweed">
    <path project="openSUSE:Factory" repository="snapshot"/>
    <arch>x86_64</arch>
    <arch>aarch64</arch>
  </repository>
  <repository name="openSUSE_Leap_15.6">
    <path project="openSUSE:Leap:15.6" repository="standard"/>
    <path project="devel:languages:rust" repository="standard"/>
    <arch>x86_64</arch>
    <arch>aarch64</arch>
  </repository>
</project>
```

Leap carries an older Rust than the workspace MSRV (`rust-version` in the root
`Cargo.toml`, mirrored by `BuildRequires: rust >= 1.85`), so its repository
adds `devel:languages:rust` to the path. Tumbleweed tracks the current
toolchain and needs no extra path. Apply it with `osc meta prj -F project.xml
home:<user>:bitty`.

## Submitting to OBS

```sh
# 1. First time only: create the package metadir and check it out.
osc meta pkg -e home:<user>:bitty bitty
osc checkout home:<user>:bitty bitty
cd home:<user>:bitty/bitty

# 2. Copy the in-tree recipe.
cp /path/to/bitty/packaging/opensuse/bitty.spec .
cp /path/to/bitty/packaging/opensuse/_service .

# 3. Enable the source services for the project, then regenerate the source.
osc service enable tar_scm recompress set_version
osc service runall

# 4. Commit; OBS builds the enabled repositories.
osc addremove
osc commit -m "bitty <version>"

# 5. Watch the build results per repository and architecture.
osc results home:<user>:bitty

# 6. Optional: propose the package for a distribution project.
osc submitrequest -m "bitty <version>" home:<user>:bitty openSUSE:Factory
```

Step 3 is the only place the `mode="disabled"` in this tree is overridden, and
it changes the OBS-side copy only: the committed `_service` keeps
`mode="disabled"` so a checkout of this repository never fetches anything.

`osc build --local-package` accepts the same files, so a build failure can be
reproduced without touching the project.

## How the zypper repository is published

OBS publishes the repository automatically once a project build succeeds; there
is no upload step in this repository and no artifact to stage. For each enabled
repository OBS writes `repodata/` (primary, filelists, other, and their
signatures) next to the RPMs and serves it from:

```text
https://download.opensuse.org/repositories/home:/<user>:/bitty/<repository>/
```

For example `.../openSUSE_Tumbleweed/` and `.../openSUSE_Leap_15.6/`. That URL
is what users add with `zypper addrepo` (`packaging/opensuse.md`). Publication
happens on the OBS side: a project can also be flagged `publish` disabled while
testing, which leaves the build results in place but serves no repository.

Repository metadata is rebuilt per publish, so a new `bitty` version appears
after `osc results` shows the repository green for every enabled architecture.
Users see it after `zypper refresh`.

## Offline and vendored builds

OBS build workers resolve crates from crates.io during `%build` (the worker has
network access), which is what `cargo build` in `bitty.spec` relies on. A fully
offline build needs the vendored crate tree: the `cargo_vendor` block in
`_service` is kept commented out because enabling it emits `vendor.tar.zst`
plus a cargo configuration the spec would have to unpack and point
`CARGO_HOME` at. Enabling it is a deliberate change to both files, not a
switch: keep the `vendor.tar.zst` as an OBS `Source1` and unpack it in `%prep`.

## Manual RPM fallback

The release workflow already publishes an RPM built by `nfpm` (see
`packaging/bitty.spec` and `packaging/fedora.md`) that installs on openSUSE.
It is a prebuilt bundle with no source build; the OBS package above is the
source path. Both provide `bitty-terminal`; do not install both.
