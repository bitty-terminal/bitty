# CTX-0839 — RSS 400MB+ accounting vs Ghostty (#1440) — evidence report

- Task: CTX-0839 — Confirm RSS 400MB+ accounting vs Ghostty (#1440)
- Issues: #1440 (this investigation), #1458 (startup-memory context, contains the 16 MiB / 2 MiB / 1 MiB / 30 MiB / 400 MiB breakdown quoted below)
- Worktree: `.worktrees/ctx-0839`, branch `carryctx/ctx-0839`, base `efe17a67`
- Method: read-only code analysis + live host reference points (`ps`, `/proc/<ghostty>/smaps_rollup`, `nvidia-smi`). No bitty binary exists in the repo `target/` (`target/debug/bitty` and `target/release/bitty` both absent; only `build/deps/examples/incremental`), so no local bitty RSS measurement was possible. No full workspace build was run (scope discipline). One `rustc` replica probe was compiled to `/tmp/opencode/` (outside the repo) to size the `Cell` layout idiom.

## 1. Verdict (one paragraph)

The 400 MB figure is most plausibly **real process RSS that is misattributed, not a real 400 MB heap of terminal state**. The bounded in-code allocations (atlas + full scrollback + batch buffers + PTY channels) sum to roughly **60–110 MB worst case in a release build**, and far less in a typical fresh session (tens of MB). The gap to 400 MB is best explained by three accounting effects, in order: **(a) debug-build fixed cost** — the workspace ships no `[profile.*]` stripping config and the only evidence-friendly binary path in CI/docs is `target/debug/bitty` (see `packaging/linux/README.md:42-46`, `justfile` `runtime-deps` gate); a debug bitty plus its dependency `.rlib`/symbol weight lands in the hundreds of MB of private RSS before any terminal state exists; **(b) shared font + GPU-driver mappings counted in RSS** — FreeType/fontconfig face objects, mapped font files, and wgpu/Vulkan loader + shader-module arenas sit in process RSS (partially `Shared_Clean`, so PSS < RSS) while contributing nothing to the heap budget; **(c) multi-process summation confusion** — each pane/PTY owns a child shell process (~3–8 MB RSS each, directly observed on the live Ghostty reference: 7 fish children at 3.2–8.4 MB) plus one forwarder thread per PTY, so summing a process tree over-counts versus the single `bitty` RSS. Separately, the `nvidia-smi bitty 65 MiB vs Ghostty 327 MiB` comparison in #1440 is **not apples-to-apples**: on the investigation host (RTX 4060 Mobile, driver 615.71.09) `nvidia-smi` today reports Ghostty at **258 MiB (G, graphics)** and does **not** list graphics-only consumers in the compute-apps query at all — i.e. `nvidia-smi` GPU MiB is VRAM-side GEM/framebuffer residency, disjoint from CPU RSS. Ghostty's larger GPU number reflects its multi-texture OpenGL working set (per-surface color textures + framebuffers), while Bitty's render path is deliberately a **single R8 coverage atlas + one transient inline texture** (see §3.1). A small GPU MiB next to a large CPU RSS is therefore the _expected_ signature of this architecture, not evidence of a leak.

## 2. Live host reference points (2026-09-28, RTX 4060 Mobile, driver 615.71.09)

- Ghostty PID 13625: `RSS 298204 KiB` (~291 MB) in `ps`, `smaps_rollup Rss: 278336 kB / Pss: 256733 kB / Pss_Anon: 221364 kB / AnonHugePages: 81920 kB / Swap: 1404884 kB (SwapPss ~same)`. So even the Ghostty baseline on this box is ~280 MB RSS with ~1.4 GB swapped — daily-driver RSS in the few-hundred-MB band is normal for a GPU terminal with shells open, and swap accounting dwarfs every in-code allocation below.
- Ghostty children: 7× `fish` at RSS 3.2–8.4 MB each. Any tool that sums the tree adds ~30–40 MB that is not terminal heap.
- `nvidia-smi`: Ghostty `258 MiB`, type `G` (graphics). `nvidia-smi --query-compute-apps` lists only `swaync` (22 MiB, C+G) and a Firefox `rdd` task (237 MiB); graphics-only processes are invisible to the compute query. Lesson for the #1440 acceptance criterion: the measurement method must name **which** `nvidia-smi` table is read (processes table vs compute-apps query) and must pair it with `/proc/<pid>/smaps_rollup` (RSS/PSS split), never with a bare `ps RSS` + `nvidia-smi` addition.

## 3. Allocation inventory (with file:line refs and byte math)

All paths below are relative to the worktree root (which mirrors `main` at `efe17a67`).

### 3.1 GPU atlas path — the largest _named_ allocation, but small

- `crates/bitty-render/src/atlas.rs:20` — `DEFAULT_ATLAS_DIMENSION: u16 = 2048`. Comment on the constant itself states the math: **2048×2048 RGBA = 16 MiB**. That comment is stale in one respect: the actual GPU texture is **R8, not RGBA** (see next point), so keep the two numbers apart.
- `crates/bitty-render/src/grid.rs:1545-1551` (`GlyphAtlas::with_dims`) — CPU-side texels: `vec![0; w*h]` bytes, **1 byte/texel** → **2048×2048 = 4,194,304 B = 4.0 MiB** resident from renderer construction (eager, not lazy; `GridRenderer::new` → `GlyphAtlas::new(dimension)` at `grid.rs:1868-1880`). Allocated once per `Runtime` (field `renderer`, `crates/bitty-runtime/src/runtime.rs:392`), **not** per pane.
- `crates/bitty-render/src/pipeline.rs:532-557` (`make_r8_texture`) + call site `:870-873` — GPU texture `R8Unorm 2048×2048` = **4 MiB VRAM minimum** (driver tiling/alignment may round up; still single-digit MiB). Contrast with the `RGBA` reading of #1458: the 16 MiB figure applies only if the atlas were RGBA; as built it is 4 MiB.
- `crates/bitty-render/src/batch.rs:79,85` — caps: `MAX_ATLAS_DIMENSION = 4096` (a 4096² R8 would be 16 MiB; admission cap only, never allocated by default), `INLINE_TEXTURE_SIZE = 1024` → transient inline texture **1024×1024×1 B = 1 MiB**, and `pack_inline_glyphs` (`batch.rs:594-690`) builds a **1 MiB `vec![0u8; side*side]` per call** — transient per frame, only on atlas-overflow frames.
- `crates/bitty-render/src/pipeline.rs:1045-1126` (`upload_atlas`) — **the hidden second copy**: `last_atlas_texels: Option<Vec<u8>>` (`pipeline.rs:414`) retains `texels.to_vec()` after every upload (`:1096`, `:1126`). Steady-state cost: **+4 MiB CPU** duplicating the atlas for dirty-diffing. Padded staging (`build_padded_full`, `batch.rs:814-826`) transiently allocates `padded_bytes_per_row(2048)=2048 ×2048` = **4 MiB** (2048 already satisfies the 256-B alignment, so no padding overhead at default size) on full uploads; strip uploads (`build_padded_strip`, `:832-850`) are proportionally smaller.
- `crates/bitty-render/src/pipeline.rs:434-448` — GPU vertex/index buffers, all created once in `GpuResources::create` (`:836-859`): fill `4096×4×48 = 768 KiB`, glyph `4096×4×52 = 832 KiB`, image 2 KiB, index `4096×6×2 = 48 KiB` → **~1.65 MiB VRAM**, fixed.
- **Atlas subtotal (default 2048, steady state): ~4 (CPU texels) + ~4 (last-upload copy) + ~4–8 (GPU texture w/ alignment) + ~1 (inline texture) + ~1.65 (batch buffers) ≈ 15–19 MB**, plus transient 1–4 MB staging during uploads. The `#1458` "16 MB atlas" line is correct only as _GPU+CPU combined, RGBA reading_; the R8 reality is roughly half that per side.

### 3.2 Scrollback + terminal state — the largest _heap_ bound, usually mostly empty

- `crates/bitty-term-state/src/scrollback.rs:18,24` — `SCROLLBACK_DEFAULT_LINES = 10_000`, `SCROLLBACK_MAX_LINES = 100_000` (clamped in `with_max_lines`, `:72-79`). Empty `Scrollback::new()` retains **~0 bytes** (a `VecDeque` with no lines; lines enter only via scroll-under-region ops, `scrollback.rs:123-160`).
- Cell size: `Cell` (`cell.rs:229-250`) = `char (4) + Style + u8 + bool + Option<HyperlinkId> + Zerowidth`. `Style` (`cell.rs:124-133`) = 3×`Option<Color>` + `Attributes`; `Color` (`bitty-vt/src/action.rs:184-192`) = `Default | Indexed(u8) | Rgb([u8;3])` → 4 B, and `Option<Color>` stays 4 B via niche-filling; `Rgb` (`action.rs:170-177`) is 3 B. `Attributes` (`cell.rs:47-64`) = 3×bool + `UnderlineStyle` + 5×bool ≈ 8 B after layout. `Zerowidth` (`cell.rs:146-149`, `[char;5]+u8`) asserts `size_of == 24` in-test (`cell.rs:779`). A standalone `rustc` replica of this exact field layout measures **`size_of::<Cell>() = 60 bytes`** (replica probe, `/tmp/opencode/cellsize.rs`; treat as ±8 B estimate — real `Color` niche-filling and `UnderlineStyle` layout may shift it a few bytes either way; the in-repo bound `size_of::<Cell>() <= 96` at `cell.rs:783` is the verified ceiling).
- Byte math at 60 B/cell, 80-col grid: **one full line ≈ 4.8 KB**; **full 10k-line scrollback ≈ 48 MB**; **100k-line hard cap ≈ 480 MB** (requires the user to raise `terminal.scrollback` to the maximum _and_ fill it — pathological, not daily-driver). Fresh/typical sessions with hundreds of retained lines: **single-digit MB**. The `#1458` "~200 bytes/line ≈ 2 MB" estimate predates the inline-zerowidth `Cell` (CTX-0389, #645) and understates a full buffer by ~24×; the corrected bound is ~48 MB full, ~0–5 MB typical.
- Per-`State` fixed extras: live grid 80×24 = 1920 cells ≈ 115 KB; damage ring, hyperlink table (`HYPERLINK_TABLE_MAX = 1024`, `state.rs:58`), zone records (`ZONE_RECORDS_MAX = 1024`, `state.rs:62`) — all KB-scale.
- Per-pane scaling: each split owns a `PaneSession { parser, state, pty, reader, writer, … }` (`runtime/panes.rs:19-37`) → **one more full scrollback bound per split** plus one PTY child process plus one forwarder thread. Single-pane use adds nothing (`pane_sessions` empty).

### 3.3 Glyph cache + font stack — bounded heap, unbounded-looking RSS

- `crates/bitty-render/src/cache.rs:37` — `DEFAULT_GLYPH_CACHE_CAPACITY = 2048` entries, strict LRU (`evict_lru`, `cache.rs:199-208`), errors never cached. Per-entry bitmap: RGB (3 B/px) or RGBA (4 B/px) of a ~6–40 px glyph → ~100 B–6 KB typical → **cache heap ≈ 0.2–12 MB**, plus `HashMap<RasterKey, CacheEntry>` overhead (`RasterKey` = `char + FontId + f32` ≈ 12–16 B + entry/node overhead ≈ 50–100 B → ~0.1–0.2 MB at 2048 entries). Bounded and hot-set friendly; **not** a 400 MB suspect.
- Behind the cache sits `FallbackRasterizer` (`fallback.rs:77-108`) wrapping `AnyRasterizer::Headless|CrossFont` (`runtime/present.rs:62-96`): the fallback chain loads **up to 1 + 6 faces** (`FONT_FALLBACK_CHAIN`, `bitty-config/src/types.rs:1572-1579` on Linux: Nerd → JetBrains Mono → monospace → DejaVu Sans Mono → symbols → emoji) at the same style/size. Each loaded face pins a FreeType face + size object inside `crossfont::Rasterizer` (`crossfont_backend.rs:37-42`) **plus** fontconfig's process-wide mapped font files and `crossfont`'s internal caches — none of which appear in any Bitty-side byte counter but all of which land in process RSS (partly shared). This is the single biggest _unaccounted_ RSS contributor after the debug binary itself, and the reason `ps RSS` exceeds the heap budget by an order of magnitude on font-heavy systems.
- Upstream font discovery is platform-default (CoreText/DirectWrite/FreeType+fontconfig, `crossfont_backend.rs:17-20`); Bitty adds no search path of its own, so font RSS is inherited from the host font installation, not tunable in-code beyond chain length.

### 3.4 Batch/vertex buffers, images, surfaces — small and capped

- `#1458`'s "multiple 4096-element buffers ≈ 1 MB" is confirmed and tightened: fill+glyph+index CPU chunks reuse the same ~1.6 MB bound per frame (`batch.rs:54-65`, `chunk_*` reuse buffers via `std::mem::take`), transient, not retained.
- Kitty images: `MAX_IMAGE_BLITS_PER_FRAME = 32`, `MAX_IMAGE_UPLOAD_BYTES_PER_FRAME = 64 MiB` (`batch.rs:110-120`), background raster cache capped at the same 64 MiB (`bitty-rich/src/background.rs:71-78`). Admission-checked _before_ allocation (`plan_image_uploads`, `batch.rs:983-1021`) — a pathological frame can transiently stage up to 64 MiB, but steady state without images is ~0.
- Headless/CPU surface: `MAX_HEADLESS_SURFACE_BYTES = 64 MiB` (`gpu.rs:562`), `headless_buffer_len` fail-closed (`gpu.rs:573-581`); a 4K headless surface is exactly at cap (4096×4096×4 = 64 MiB). Real-window path allocates no such CPU buffer (composites on-GPU).

### 3.5 PTY / threads / IPC — small per unit, multiplied per pane

- `bitty-pty/src/reader.rs:56-63`: `READ_CHUNK_SIZE = 8 KiB`, `CHANNEL_CAPACITY_CHUNKS = 16` → **128 KiB bounded channel per reader** (+1 in-flight chunk). One reader + one forwarder thread per PTY (primary + one per split). Default thread stacks are 8 MiB _virtual_ (mostly untouched RSS).
- No custom/global allocator (`global_allocator` absent repo-wide); no `[profile.release]` stripping/lto configured (no `[profile.*]` in workspace or member manifests) — debug builds carry full symbols, confirming route (a) of the verdict.

### 3.6 Plugin hosts / Lua VMs — quota-bounded, lazy in the safe path

- `bitty-lua/src/lib.rs:109,114`: `RC2_MEMORY_PER_PLUGIN_BYTES = 32 MiB` (builder hard quota + `total_memory()` polling), `RC2_MEMORY_AGGREGATE_BYTES = 512 MiB`. Safe startup path loads no third-party plugins (safe-startup invariant in repo guidance); steady-state Lua RSS without plugins is ~0. Each active plugin VM can add up to its 32 MiB quota — relevant only with plugins installed, which the #1440 reporter did not enumerate.

## 4. Top-3 contributors (byte estimates, release build, one window, no plugins)

1. **Font + GPU-driver working set (tens of MB RSS, ~0 MB Bitty heap): ~30–80 MB.** FreeType faces for up to 7 chain faces, fontconfig mapped fonts, `libfontconfig`/`freetype` shared libs, wgpu/Vulkan loader + compiled shader modules + per-device arenas. Evidence: nothing in Bitty's heap counters covers it; Ghostty's `smaps_rollup` shows the pattern (`Shared_Clean 26 MB`, `AnonHugePages 82 MB`, `Pss_File 35 MB`). Reduction requires chain trimming / lazy face loading, not cache tuning.
2. **Atlas complex, steady state: ~15–19 MB (of which ~4 MB is a removable duplicate).** 4.0 MiB CPU texels + 4.0 MiB `last_atlas_texels` clone + 4–8 MiB GPU texture + 1 MiB inline texture + 1.65 MiB batch GPU buffers. The single cheapest safe saving is dropping the `last_atlas_texels` clone (diff against `GlyphAtlas::texels()` via a rolling hash or generation+strip hint) — saves a flat **4 MiB CPU** with no visual change (correctness/perf tradeoff to be reviewed, not done here).
3. **Scrollback heap bound: 0–48 MB by fill (typical single-digit MB).** 60 B/cell × 80 cols × up to 10k lines. Per extra split pane: another 0–48 MB bound + ~128 KiB channel + child shell RSS (~3–8 MB each, separate PIDs). Worst-case 100k-line user config: up to ~480 MB — the only path by which in-code allocations alone _can_ reach the reported magnitude, and it requires deliberate configuration plus a full buffer.

## 5. Ghostty comparison (high level, from architecture knowledge)

- Ghostty (Zig): one process, per-surface OpenGL renderer with **per-surface color textures + framebuffers** (hence large `G`-type VRAM: 258–327 MiB depending on window count/size) and a custom allocator + font stack (`font/CodepointResolver`, FreeType+harfbuzz, per-codepoint fallback via discovery). Its CPU RSS (~280 MB on this host with swap spillover) already includes its font atlas working set in-process.
- Bitty: one process, wgpu, **single shared R8 coverage atlas (4 MiB) + transient 1 MiB inline texture**, per-pane `State`+PTY rather than per-surface render state, `GlyphCache` 2048 + shelf-packed atlas with frame-consistent wholesale eviction (CTX-0531). Smaller GPU footprint by design; CPU RSS dominated by the same externalities (fonts, drivers, debug symbols) rather than by the atlas.
- Bottom line for #1440: comparing `nvidia-smi` GPU MiB across the two is a category error (VRAM residency vs CPU RSS, graphics vs compute tables). The valid comparison is **CPU PSS from `smaps_rollup` (release builds, same window/pane count, same font chain length) plus `nvidia-smi` graphics-table MiB as a separate column**.

## 6. Recommended next steps (for the owning commander; no code changed here)

1. **Fix the measurement method first (acceptance item 1 of #1440).** Define: release binary (`cargo build --release`), one window / one pane, fixed font size, `smaps_rollup` Rss/Pss/Private_Dirty + `nvidia-smi` graphics table + per-child `ps RSS`. Record Ghostty under identical conditions on the same host. Expected saving: none directly — but kills all phantom regressions and unblocks every later claim. Owner: perf/budget task; deliverable is a `bitty-perf` probe or `recording/` procedure, not render code.
2. **Document/verify release-vs-debug in #1458 Phase 1.** Add (or confirm) `[profile.release] strip/reduced-debug` + codegen policy and publish release RSS next to debug RSS. Expected saving: **100+ MB** of private RSS for users currently running debug builds (the most likely single cause of a 400 MB _startup_ number).
3. **Drop the `last_atlas_texels` duplicate** (`pipeline.rs:414,1096,1126`). Expected saving: flat **4.0 MiB CPU RSS**; needs a reviewer-approved diffing strategy (rolling checksum vs full compare cost). Small but trivially safe-shaped.
4. **Atlas lazy sizing** (512² → grow to 2048 only on demand; #1458 Phase 1). Expected saving: **~3.75 MiB CPU + ~3.75 MiB GPU** for CJK-light sessions that never fill 512²; zero effect once the working set needs 2048² (eviction counters in `GlyphAtlas` will show it).
5. **Scrollback default 10k → 5k** (#1458 Phase 1). Expected saving: halves the _worst-case bound_ (48 → 24 MB); near-zero steady-state effect (empty buffer costs nothing). Do only with the config-compat story (`terminal.scrollback` range already `0..=100_000`, `scrollback.rs:22-24`).
6. **Lazy-load fallback faces** (load chain tails on first missing-glyph, not at `load_font`). Expected saving: **Single-digit MB RSS + faster startup** on systems where 4–5 of 6 tails are never touched; measure via `smaps_rollup` before/after, since the saving is in fontconfig/FreeType mappings, not Bitty heap.
7. **Per-pane accounting note in the budget doc.** State the per-split cost explicitly (second scrollback bound + PTY + thread + child shell) so multi-pane daily-driver RSS (~+10–60 MB per busy split) is never re-reported as a leak.
8. **Do not chase** `GlyphCache` capacity, batch-chunk sizes, or PTY channel sizes: all are already bounded, LRU/chunked, and sum to low-single-digit MB. The `#1458` "~30 MB expected baseline" is consistent with this report's ~15–25 MB steady-state heap finding; the 400 MB observation sits outside the heap entirely.

## 7. Limits of this report

- No bitty process was running, so **no measured bitty RSS exists**; all byte math is from constants + layout probes, not from a profiler. The `Cell = 60 B` figure is a replica-struct probe, not `size_of!` against the real type — confirm with a one-line unit print before citing it as exact.
- GPU-side numbers (tiling, alignment, driver arenas) are bounds, not captures; `nvidia-smi` graphics-table sampling on a bitty window is still open (needs a release build + display server access, deliberately out of scope for this time-bounded pass).
- Swap (`SwapPss ~1.4 GB` on the Ghostty reference) means any cold-page RSS reading understates the true working set; the budget method in §6.1 must pin warm-up (scroll + render + font-touch) before sampling.
